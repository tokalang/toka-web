## See The Boundary In The Code

Toka keeps an ownership transfer visible at the call site and in the function contract:

```toka
shape Resource(val: i32)

fn keep(cede item: Resource) -> Resource {
    return cede item
}

fn main() -> i32 {
    auto item = Resource(val = 42)
    auto kept = keep(cede item)
    if kept.val != 42 {
        return 1
    }
    return 0
}
```

Toka is a public preview, not a stable 1.0 compatibility promise. Use an exact
published tag when you are ready to install an SDK.

The canonical project name is **Toka systems programming language**, maintained
at [`tokalang/toka`](https://github.com/tokalang/toka). It is unrelated to the
historical Toka Forth projects, Tokelang, and other similarly named Toka or
Toke projects.

## RC12 At A Glance

Toka `v1.0.0-rc.12` is a published Public Preview release candidate. The 1.0
language semantics are frozen during stabilization: current work focuses on
documentation, ecosystem adoption, qualification, and bug fixing rather than
new language features.

| Platform | RC12 status |
| :--- | :--- |
| Linux x86_64 | Published Tier 1 SDK archive |
| Linux aarch64 | Published Tier 1 SDK archive |
| macOS x86_64 | Published Tier 1 SDK archive |
| macOS aarch64 / Apple Silicon | Published Tier 1 SDK archive |
| Windows / MSYS2 | Source-build and dogfood path; no RC12 SDK archive |
| WSL2 / WASI | Available or experimental; not a 1.0 blocking target |

Known boundaries: RC12 remains a prerelease; the language is not self-hosted;
and the ecosystem is young. RC12 changes DX, CLI diagnostics, and documentation;
it does not change language semantics or ownership rules.

## Design Goal

Toka starts from two baselines: predictable zero-cost performance and strong static safety. The compiler also exposes machine-readable semantic facts so editors and AI tools can inspect the same boundaries that developers review. With those foundations in place, the language asks how direct, compact, and maintainable systems code can become without hiding the semantics that make systems programming hard.

Toka does not pursue minimal syntax for its own sake. It pursues the minimum surface needed to expose real systems semantics: ownership transfer, mutation, rebinding, nullability, error propagation, async suspension, FFI boundaries, and representation-level access.

<CardGrid stagger>
	<Card title="Performance As A Baseline" icon="rocket">
		Toka has no garbage collector and is compiled ahead of time through LLVM. Resource and representation costs are intended to stay visible and predictable rather than being hidden behind a default runtime layer.
	</Card>
	<Card title="Static Safety As A Baseline" icon="shield">
		Resource flow, borrowing, nullability, rebinding, and cleanup are checked through explicit contracts such as PAL and `cede`. When a relationship cannot be proven locally, Toka should be conservative rather than push a full lifetime calculus into ordinary code.
	</Card>
	<Card title="Payload And Handle Separation" icon="puzzle">
		Plain names operate on object payloads. Hats such as `&`, `*`, `^`, and `~` expose handle identity only when code genuinely needs to borrow, own, share, forward, or rebind that layer.
	</Card>
	<Card title="Complexity With A Job" icon="star">
		Every piece of surface complexity should earn its place by revealing a systems boundary that would otherwise become implicit, distant, or harder to audit.
	</Card>
	<Card title="Integrated Project Tooling" icon="setting">
		The `toka` command manages project creation, single-file runs, package resolution, build orchestration, tests, formatting, and documentation around `package.tk` and `build.tk`.
	</Card>
	<Card title="AI-Ready Compiler Facts" icon="document">
		Structured diagnostics, semantic context, API contracts, and focused ownership or capability evidence let an editor or AI tool verify an edit against compiler facts. They do not replace project tests or claim that a model writes correct code on its own.
	</Card>
</CardGrid>
