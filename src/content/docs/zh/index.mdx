## 在代码中看见边界

Toka 让所有权转移同时出现在调用点与函数契约中：

```toka
shape Resource(val: i32)

fn keep(cede item: Resource) -> Resource {
    return cede item
}

fn main() -> i32 {
    auto item = Resource(val = 42)
    auto kept = keep(cede item)
    if kept.val != 42 {
        return 1
    }
    return 0
}
```

Toka 当前处于 Public Preview，并非稳定的 1.0 兼容性承诺。安装 SDK 时请使用一个明确、已发布的 tag。

本项目统一使用名称 **Toka systems programming language**，官方仓库为
[`tokalang/toka`](https://github.com/tokalang/toka)。它与历史上的 Toka Forth、
Tokelang，以及其他同名或近似命名的 Toka / Toke 项目无关。

## RC10 状态概览

Toka `v1.0.0-rc.10` 是已经发布的 Public Preview release candidate。在稳定化
阶段，1.0 语言语义已经冻结；当前工作集中于文档、生态采用、资格验证和缺陷修复，
不再增加语言新特性。

| 平台 | RC10 状态 |
| :--- | :--- |
| Linux x86_64 | 已发布 Tier 1 SDK archive |
| Linux aarch64 | 已发布 Tier 1 SDK archive |
| macOS x86_64 | 已发布 Tier 1 SDK archive |
| macOS aarch64 / Apple Silicon | 已发布 Tier 1 SDK archive |
| Windows / MSYS2 | 源码构建与 dogfood 路径；没有 RC10 SDK archive |
| WSL2 / WASI | 可用或实验性路径；不是 1.0 阻塞目标 |

已知边界：RC10 仍是 prerelease；语言尚未自举；生态仍然年轻；成功执行
`toka run` 时也可能出现来自 SDK 构建模块的 `W0408` warning noise。

## 用 TokaKV 运行真实程序

[TokaKV](https://github.com/tokalang/tokakv) 是使用纯 Toka 实现的官方嵌入式
键值存储引擎。从干净的 RC10 SDK 开始：

```bash
toka new tokakv_hello
cd tokakv_hello
toka add tokakv
```

用下面的内容替换 `src/main.tk`：

```toka
import std/io::{println}
import official/tokakv::{TokaKvEngine}

fn main() -> i32 {
    auto db = TokaKvEngine::open(string::from("hello.tokakv")).unwrap()
    db.put(string::from("language"), string::from("Toka")).unwrap()

    auto value = db.get(string::from("language")).unwrap().unwrap()
    println("{}", value)

    db.close().unwrap()
    return 0
}
```

运行 `toka run`，最终输出为 `Toka`。这条完整流程已经使用已发布的 RC10 SDK
和公开 `tokakv` 包完成验证。为保持紧凑，示例使用了 `unwrap()`；生产代码应显式
处理存储和 I/O 错误。

TokaKV 当前是单进程嵌入式 preview 引擎，compaction 范围为 L0-to-L1；更深层级、
分布式复制和 Redis 协议服务端不在当前边界内。

## 设计目标

Toka 从两个底线出发：可预测的零成本性能，以及强静态安全。编译器还会输出机器可读的语义事实，让编辑器和 AI 工具能检查开发者正在审阅的同一组边界。在这些前提下，Toka 追问的是：系统代码能否在不隐藏真实系统语义的前提下，更直接、更紧凑、更可维护。

Toka 不以“最少语法”为目标。它追求的是：在真实系统语义不被隐藏的前提下，触摸到所需的最小表层。所有权转移、可变性、重绑定、可空性、错误传播、异步挂起、FFI 边界，以及表示层访问，都应该在真正发生作用的位置可见。

<CardGrid stagger>
	<Card title="性能是底线" icon="rocket">
		Toka 没有垃圾回收器，并通过 LLVM 进行 AOT 原生编译。资源成本和表示成本应当保持可见、可预测，而不是被默认运行时层遮住。
	</Card>
	<Card title="静态安全是底线" icon="shield">
		资源流、借用、可空性、重绑定和清理通过 PAL、`cede` 等显式契约接受检查。当某种关系无法被局部证明时，Toka 应当保守拒绝，而不是把完整生命周期演算压到日常代码表层。
	</Card>
	<Card title="Payload 与 Handle 分离" icon="puzzle">
		裸名操作对象 payload。只有代码确实需要借用、拥有、共享、转发或重绑定 handle 层时，才使用 `&`、`*`、`^`、`~` 等帽子。
	</Card>
	<Card title="复杂性必须有职责" icon="star">
		每一份表层复杂性都应该证明自己揭示了一个真实系统边界；否则这个边界就会变得隐式、遥远，或者更难审计。
	</Card>
	<Card title="内建项目工具链" icon="setting">
		`toka` 命令围绕 `package.tk` 和 `build.tk` 管理项目创建、单文件运行、包解析、构建编排、测试、格式化和文档生成。
	</Card>
	<Card title="面向 AI 的编译器事实" icon="document">
		结构化诊断、语义上下文、API 契约，以及聚焦的所有权或能力证据，使编辑器或 AI 工具可以根据编译器事实验证修改。它们不取代项目测试，也不宣称模型会自行写出正确代码。
	</Card>
</CardGrid>
